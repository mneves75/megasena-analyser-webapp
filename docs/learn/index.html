6 Mega-Sena Analyzer · Onboarding

Trilha do Sistema

Entenda o sistema antes do código

Esta é a versão interativa da trilha de onboarding. O conteúdo completo e rastreável está nos arquivos Markdown (01–10); aqui você navega com diagramas, busca, glossário e widgets ao vivo. O código é a fonte primária de toda afirmação.

O Mega-Sena Analyzer baixa sorteios oficiais da CAIXA para um SQLite local, calcula estatísticas com engines em TypeScript num servidor Bun (server.ts, porta 3201) e mostra tudo num app Next.js 16 (porta 3000). Ele analisa o passado; não prevê o futuro.

Arquitetura em um diagrama

graph TD Browser["Navegador"] subgraph NextProc["Next.js (3000)"] MW["proxy.ts: nonce + CSP"] RSC["Server Components / Actions"] RW["rewrite /api/* (next.config.js)"] end subgraph BunProc["Bun (3201) - server.ts"] API["Handlers /api/* + rate limit + CORS + auditoria"] ENG["StatisticsEngine / BetGenerator / *AnalysisEngine"] DB[("SQLite (bun:sqlite)")] end CAIXA["API CAIXA"] PULL["scripts/pull-draws.ts"] Browser --> MW --> RSC RSC -->|fetchApi| API Browser -->|/api/*| RW --> API API --> ENG --> DB PULL -->|fetchDraw| CAIXA PULL --> DB 
Fluxo: Navegador → Next.js (3000) → fetchApi → Bun API (3201) → engines → SQLite. Ingestão: pull-draws.ts → CAIXA → SQLite.

Dois processos

Next.js (3000) renderiza; Bun (3201, server.ts) é o único que toca o banco (bun:sqlite).

RSC chama a API

Server Components/Actions usam fetchApi (lib/api/api-fetch.ts); nada de SQL no Next.

Sem login

Sem conta de usuário; user_bets existe no schema mas é tabela morta.

Leia em detalhe: 01-system-overview.md.

Capítulo 01

Visão geral do sistema

O que o sistema faz, para quem, e como as peças de runtime se encaixam.

Modelo mental

Uma biblioteca com dois funcionários: o arquivista (Bun/server.ts) cuida do acervo (SQLite) e responde em JSON; o recepcionista (Next.js) atende o público e, quando precisa de dados, pergunta ao arquivista.

Analisa padrõeslib/analytics/*
Gera apostas por orçamentolib/analytics/bet-generator.ts

Apresenta páginasapp/dashboard/*
Premissa explícita do produto: loteria não é previsível. Avisos em app/page.tsx, app/about/page.tsx e na página do gerador.

Capítulo 08

        
Exercícios

        
Pratique do entendimento à mudança. Gabaritos escondidos — tente antes de abrir.

        
Fácil · Liste as 5 rotas /api/*
/api/health, /api/dashboard, /api/statistics, /api/trends, /api/generate-bets (ver apiHandlers em server.ts).

        
Médio · Por que as frequências podem ficar erradas após importar?
Faltou rodar StatisticsEngine.updateNumberFrequencies(); number_frequency é cache derivado.

        
Médio · Onde a produção recusa iniciar sem segredo?
server.ts: bloco que faz process.exit(1) sem IP_HASH_SECRET, antes de runMigrations() (fail-closed).

        
Difícil · Prove a defesa em profundidade da unicidade
Escreva um teste que insira números repetidos e espere ABORT (trigger da migração 007); use VITEST_FORCE_FILE_DB=1.

Widget ao vivo

        
Otimizador de apostas (porta de bet-generator.ts)

        
Esta é uma reimplementação fiel, em JavaScript, do algoritmo de programação dinâmica buildOptimizedBetSizes(budget), usando os preços reais de lib/constants.ts. Ele escolhe tamanhos de aposta (6–20) priorizando, nesta ordem: gastar o máximo do orçamento, maximizar a cobertura de números, usar menos apostas e, por fim, cobrir mais números.

        

          

            

              
              
            

            

          

          

          

          

        

        
Lembre: isto não dá vantagem preditiva. Ele só otimiza o uso do orçamento. Loteria é aleatória.
