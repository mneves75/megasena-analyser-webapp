# 2026-09-15 — v1.13.2: Bun 1.4.2, Next.js 16.3.5, rate limit por visitante, DB #3057

## O que foi para produção

- Imagem `v1.13.2` com Bun **1.4.2** (1.4.2 corrige crash/travamento de GC em
  `splice`/`shift` sobre musl, a libc da imagem Alpine). Next.js 16.3.5 e overrides
  fecham todos os advisories: `pnpm audit --prod` e o audit completo zerados.
- Banco #3051 → #3057, conferido contra a API da CAIXA (#3055 idêntico em dezenas,
  data e rateio). Pós-deploy: `integrity_check=ok`, 0 lacunas, `audit_logs` e
  `log_events` preservados.

## Achados de segurança corrigidos

- **SSR sem IP do visitante.** Páginas SSR e a server action chamavam a API por
  loopback sem headers de cliente: sem `INTERNAL_API_SECRET`, todos dividiam o bucket
  de `127.0.0.1`; com o segredo, a geração via server action ficava sem limite. Agora
  os headers de IP confiáveis são repassados byte a byte. Prova ao vivo em produção:
  carregar `/` custou 2 do meu bucket (SSR + leitura), `/about` (controle) custou 1.
- **Isenção por valor é burlável.** A primeira versão isentava quando o IP resolvido
  era igual ao peer loopback; o review de spec mostrou que `CF-Connecting-IP: 127.0.0.1`
  forjado (ou um valor inválido que cai para o peer) comprava a isenção. O critério
  certo é a PRESENÇA de header de IP, não o valor resolvido.
- **`Purpose: prefetch` sem CSP.** O matcher do `proxy.ts` pulava documentos HTML
  pré-carregados. Só o prefetch RSC do router pode pular.

## Deploy: defeitos que só apareceram executando

- O tarball de deploy nunca incluiu `patches/` (copiado pelo Dockerfile desde o patch
  do minimatch). Produção só construía porque o diretório guardava uma cópia antiga;
  staging falhou com `"/patches": not found`. Hoje o script confere cada fonte de COPY
  contra o tarball antes do upload.
- Essa guarda deu **falso positivo** na primeira execução: `printf | grep -q` sob
  `pipefail` recebe SIGPIPE quando o grep casa cedo. O teste inicial passou porque o
  harness não tinha `pipefail`. Teste o bloco extraído no MESMO modo de shell.
- `--with-db` fazia `docker exec` no contêiner de produção fixo; apontar para staging
  teria fotografado o banco de produção. Agora `CONTAINER` é parâmetro.
- O cutover apagava `-wal`/`-shm` sempre e o rollback copiava o backup com o contêiner
  que falhou ainda de pé. Agora backup/swap/rollback tratam main+WAL+SHM como unidade
  (simulado em 3 cenários antes de produção; o backup real de hoje levou os sidecars).
- O build da imagem passou para ANTES do snapshot, encurtando a janela em que linhas
  de auditoria/log escritas em produção ficam fora do arquivo trocado.

## Staging real ≠ script de staging

- O staging vivo é o projeto compose baseado em tag, deployado pelo `deploy.sh`
  canônico com `REMOTE_DIR`/`PUBLIC_URL`/`CONTAINER`. O `deploy-staging.sh` mira um
  diretório legado e colide no nome do contêiner. Antes de alterar config de staging,
  leia os labels `com.docker.compose.project.*` do contêiner em execução.

## Ambiente (não é bug do repo)

- Um limpador externo apaga `~/Library/Caches` (sumiram `node_modules` e os browsers
  do Playwright durante a sessão), e a extração do Playwright travou duas vezes a 0% de
  CPU sob antivírus. Contorno que funcionou: baixar o zip oficial com `curl`, extrair
  com `ditto` e rodar o E2E com `PLAYWRIGHT_BROWSERS_PATH` fora de `~/Library/Caches`.
- `pnpm add` travou ocioso ao final; `pnpm install --frozen-lockfile` confirmou que
  manifesto, lockfile e `node_modules` já estavam consistentes.
