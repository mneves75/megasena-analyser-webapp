## `deploy.sh --db-only`

- `--with-db` acoplava o refresh de banco a tarball + rebuild + cutover. Quando só os
  dados mudam, isso reconstrói a mesma imagem à toa. Novo modo `--db-only`: pula
  empacotamento e build, mantém a tag viva, faz snapshot → ingestão local → swap →
  health gate.
- Defeitos encontrados em review e corrigidos (todos com check runnable):
  - `grep -oP 'v[0-9.]+'` **truncava tags de prerelease** (`v1.13.1-beta.1` → `v1.13.1`).
    No deploy normal isso reescrevia o compose para uma tag inexistente; no `--db-only`
    fazia o health gate falhar *depois* do swap. Agora `v[A-Za-z0-9_.-]+`.
  - `${WITH_DB:+...}` expandia sempre, porque a variável guarda a *string* `"false"`.
    Todo deploy normal se anunciava como "(with DB refresh)". Testar a flag, não o
    comprimento dela.
  - O health gate do `--db-only` era **vacuamente verdadeiro**: `VERSION` derivava da
    tag viva, então a asserção passava mesmo se o swap falhasse. Agora afirma
    `lastContestNumber` do `/api/health` público contra o máximo ingerido.
  - `VACUUM INTO` recusa sobrescrever — um snapshot de uma execução anterior fazia o
    deploy morrer na largada. Limpeza antes e depois.
  - Sem novos concursos, o script parava o contêiner para trocar um banco idêntico.
    Agora sai sem tocar em produção (testado de verdade: uptime seguiu crescendo).
  - `rm -f "$TARBALL"` no fim podia apagar o tarball de um deploy concorrente.

## Janela de perda conhecida (não resolvida)

## Staging: portas em `0.0.0.0`

- `megasena-staging/docker-compose.yml` publicava `"3100:80"` e `"3401:3201"` sem IP
  de host → Docker liga em todas as interfaces, inclusive a pública, embora
  `NEXT_PUBLIC_BASE_URL` deixe claro que a intenção era só a tailnet. Portas
  publicadas pelo Docker também passam por cima do UFW (cadeia DOCKER-USER).
- Corrigido para `<tailnet-ip>:3100:80` / `<tailnet-ip>:3401:3201`; staging continua
  saudável pela tailnet, produção intacta.
- **Não verificado:** se essas portas eram alcançáveis da internet. A sonda externa
  deu timeout, mas o controle positivo mostrou que 80 e 443 do mesmo IP também dão
  timeout deste notebook — ou seja, o caminho de rede não chega lá e o resultado
  negativo não prova nada. Um negativo sem controle positivo não é evidência.
