# 2026-08-22 — v1.13.x: Bun 1.4 estável, Next 16.3.2, deploy canônico e staging alinhado

## Runtime & dependências

- Imagem de produção migrou de canary para **Bun 1.4.0 estável**
  (`oven/bun:1.4.0-alpine@sha256:0723557…`, verificado via `docker buildx
  imagetools inspect`); `.bun-canary-revision` removido — pin estável é
  auto-descritivo.
- Next.js 16.3.0 → 16.3.2; `engines.bun`/`.bun-ci-version` → 1.4.0.
- Fato-checagem do SIGSEGV de build: use-after-free de napi thread-safe
  function no `next-swc` (oven-sh/bun#36866), corrigido por #34067 no 1.4.0.
  O builder continua Node 22.23.2 até `next build` sob Bun ser revalidado em
  CI; o standalone já roda sob Bun (`bun --bun ./server.js`) — padrão mantido.
- `pnpm minimumReleaseAge` (1440 min) bloqueia também installs congelados:
  lockfile com versão <24h exige `minimumReleaseAgeExclude` temporário.
  Exclusões do lote 16.3.2 podadas por tarefa agendada (`9527a1d9`, 10:52Z).
- Override novo: `nanoid >=3.3.18 <4` (GHSA-2v37-7h3g-55p8 via next>postcss).
  Sempre limitar overrides em `<próximo major>` — a primeira tentativa sem
  teto resolveu postcss>nanoid para v6 ESM-only.

## Deploy canônico

- `megasena-deployment-private/megasena-analyser/deploy.sh` é o caminho único:
  tarball → build da imagem na VPS (sem downtime) → cutover com health gate
  (`compose up -d --wait`) + rollback automático → verificação pública da
  `/api/health`. `--with-db` cobre o refresh do banco. `deploy-docker.sh` e
  `sync-database.ts` foram removidos (o sync apontava para alias SSH morto).
- **Nunca copiar SQLite vivo com scp**: transações confirmadas podem estar no
  `-wal`. Snapshot consistente com `VACUUM INTO` dentro do contêiner:
  `docker exec -i megasena-analyzer bun -` + script curto.
- Armadilha reincidente no swap de db: após `mv`/`cp`, o arquivo fica root e o
  contêiner escreve como UID 1000 → crash-loop exit 2. Fix: `chown 1000:1000`.
- Rollback: tag anterior da imagem permanece na VPS + backups em
  `db/backups/`.
